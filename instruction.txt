## 7. Core Ticket Processing Logic

### 7.1 Ticket Identification

TRACKER ID is the actual ticket number.

TRACKER HIST ID is only the historical movement identifier.

Identify all distinct TRACKER IDs having at least one record with:

ASSIGNED_TO_GROUP = DS

Use case-insensitive and whitespace-trimmed comparison.

All ticket counts must use distinct TRACKER ID.

Never count TRACKER HIST ID as a ticket.

### 7.2 Historical Sorting

For each TRACKER ID:

- Sort TRACKER HIST ID numerically in ascending order.
- Preserve every historical record.
- Identify duplicate or invalid history IDs as data-quality exceptions.

### 7.3 First DS Assignment

Find the first history record where:

ASSIGNED_TO_GROUP = DS

Capture:

- First_DS_Tracker_Hist_ID
- DS_Assigned_User
- DS_Assigned_Date = UPDATE_DT
- SHORT_DESCRIPTION

This is the beginning of DS ownership for aging calculations.

### 7.4 Current Ownership

Find the latest history record for each TRACKER ID.

If the latest ASSIGNED_TO_GROUP = DS:

DS_Ticket_Status = Open

Otherwise:

DS_Ticket_Status = Done

Do not determine ownership from TRACKER STATUS alone.

### 7.5 Movement Tracking

Identify:

- First DS assignment
- DS to another team
- Another team to DS
- Subsequent DS transfers
- Latest ownership

A ticket that leaves DS and returns must be recognized as a returned ticket.

Maintain a complete movement audit.

## 8. Historical Date Range Calculations

The application must support historical reporting, not merely current ticket status.

Use UPDATE_DT as the effective assignment date.

Reconstruct ownership as of:

- Opening snapshot: end of the day before Report Start Date.
- Closing snapshot: end of Report End Date.

Only history records effective on or before the respective snapshot may be used.

For each ticket, maintain the sequence of ownership changes.

### 8.1 Opening Balance

Count distinct TRACKER IDs owned by DS at the opening snapshot.

### 8.2 New Tickets

Count distinct TRACKER IDs whose first DS assignment occurred within the selected reporting period.

### 8.3 Completed Tickets

Identify distinct TRACKER IDs transferred from DS to another team during the reporting period and not owned by DS at the closing snapshot.

### 8.4 Returned Tickets

Identify distinct tickets that were outside DS at the opening snapshot or after a previous transfer and returned to DS during the reporting period.

Keep this KPI separate.

### 8.5 Closing Balance

Calculate the actual distinct ticket count owned by DS at the closing snapshot.

Show the movement reconciliation:

Opening Balance + New Tickets + Returned Tickets - Completed Tickets = Closing Balance

Because a ticket can have multiple movements within a period, implement consistent distinct-ticket counting and report any reconciliation difference separately.

The historical ownership snapshot is the final authority for closing balance.

## 9. Aging Analysis

Calculate aging only for tickets owned by DS at the closing snapshot.

Ticket age:

Report End Date - First DS Assignment Date

Use calendar days.

Aging buckets:

- Less than 2 days: 0–1
- 2–4 days: 2–3
- 4–7 days: 4–6
- 2 weeks: 7–13
- 3 weeks: 14–20
- 4 weeks: 21–27
- More than 1 month: 28+

Split the tickets into:

- New Format: SHORT_DESCRIPTION contains New Format.
- Others: all remaining tickets.

Create a detailed aging summary and a chart.

The sum of all aging buckets must equal the closing balance.

## 10. SLA Analysis

SLA condition:

- SHORT_DESCRIPTION contains SLA.
- FOLLOW_UP_DT is earlier than Report End Date.

Use the follow-up date available as of the closing snapshot.

Calculate:

- Total open SLA tickets
- SLA missed
- SLA not missed
- Missing follow-up dates
- SLA missed percentage

Non-SLA tickets must never be flagged as SLA missed.

Provide New Format/Others classification where applicable.
